# 单位拥堵与导航审计（2026-10-18）

负责代理：`simulation_bug_audit`。改动范围是 `src/sim.js` 的命令分配/导航/RTS 移动，以及独立模块 `src/crowd-navigation.js`。未改模型、第一人称相机或玩家手动驾驶控制。没有导入第三方代码。

## 复现与根因

同一台 i5-12400F、Node v24.14.0，固定 0.05 秒模拟步长，各场景运行 60 秒。混编包含坦克、步战、火炮、火箭、防空与突击炮。到达定义为订单结束且距自身分配终点小于 35u；持续卡住定义为仍有订单、最后 5 秒净位移小于 8u。

| 场景 | 修复前到达 | 修复后到达 | 修复前持续卡住 | 修复后持续卡住 |
|---|---:|---:|---:|---:|
| 24 辆开阔地 | 14/24 | 24/24 | 10 | 0 |
| 48 辆开阔地 | 35/48 | 48/48 | 13 | 0 |
| 48 辆通过 192u 窄口 | 24/48 | 48/48 | 24 | 0 |
| 两队各 24 辆对向交汇 | 28/48 | 48/48 | 20 | 0 |
| 48 辆绕建筑与矿山 | 23/48 | 48/48 | 25 | 0 |

修复后每一个模拟 tick 都检查单位圆形碰撞范围的重叠和地形占用：上述五组单位间最大重叠 **0u**，进入不可通行地形 **0 次**。这些是给定场景的行为证据，不是所有地图、任意数量、无限时长的保证。

旧实现主要问题：所有单位必须挤进同一条 A* 格心路径；固定 40u 编队与 14u 停止误差让前排堵住后排；单位排列按选择数组，而非行进前后顺序；分离向量可能抵消前进，重复命令又清空已有路径。空间索引每 tick 会重建，当前复现没有证据表明它是主因。

## 实现

1. 编队围绕行进方向分配前后排；前排单位分配前排终点，稳定 ID 作为最终平局顺序。普通间隔至少为最大单位半径的 4 倍加 12u，混编样例为 96u，留出穿行空间。散开阵形进一步加宽。
2. 障碍导致终点回退时，已有终点在本次命令中临时保留，后续单位选择其它实际可用位置。命令结束即完成分配，不持有全地图资源锁。目标位置按完整单位半径检查岸线/地形。
3. A* 格心是导航提示；只有完整半径沿线可通行才向前平滑。建筑拐角不能因为离格心近就提前切角。每次最多向前检查 7 个路径点，长路径按 ID 分散到 4 个 tick 中检查，临近终点保留及时检查。
4. 移动每 tick 在有限的 11 个方向中选择可行方向，使用空间索引查询近邻，完整单位碰撞半径和建筑占地都保留。不会靠关碰撞、瞬移或穿墙解决拥堵；也不会推走手动驾驶的玩家。
5. 1.2 秒没有至少 8u 的目标进展时，进入 FIFO 局部重评队列，每 tick 最多处理 2 个请求，总 A* 搜索仍受原 10 次预算限制。动态占位把粗网格邻格全部堵住时允许回退静态路线，两次搜索都计入预算，实际移动仍检查真实碰撞。新低 ID 请求只能排到队尾；失效订单/已死亡单位/手动驾驶单位不会继续占队列。短时保持绕行路径，防止下一帧平滑又切回堵点。
6. 同一组单位重复点击同一目的地复用编队终点和有效路径，不重新洗牌。命令计划缓存最多 32 条。Shift 队列到达后继续下一个终点，落位后完全停止。

运行时近邻查询限定在局部空间桶；没有每帧遍历全图单位对。命令分配的终点冲突检查只发生在下达命令时。测试中的全单位对重叠测量是离线验证代码，不属于游戏运行时。

## 用户 ZIP 调度思路的实际吸收

另一代理核读了用户 ZIP 中 `following.py`、`reservations.py` 和 `traffic.py` 的相关实现。本项目独立采用其中“观察实际释放后才能放行，等待超时只唤醒重新评估”和 worker 有界轮次让出的原则，没有搬运工业控制代码。新增 `crowdWaiting` 保存实际观测的阻挡者 ID；阻挡消失/抵达/新命令时清理。新增 FIFO 请求队列把预算重评与实际占位检查分开。

独立行为测试把手动驾驶玩家车辆停在一格宽通道中：后车等待 **25 秒**，超过多轮重评周期，依然保留原目的地且不能穿越或挤动玩家；只有玩家实际驶离后，后车才到达终点。游戏不采用会因倒计时结束而忽略真实占位的预留租约。

另一个测试建立 24 条独立受阻车道：8 秒内每个等待单位都得到实际重规划，最高 ID 与最低 ID 的重评轮数差不超过 1；同时保持碰撞与原命令，验证不会被前面实体长期抢光预算。

## CPU 成本与边界

完整机器可读数据：[crowd-navigation-metrics.json](crowd-navigation-metrics.json)。

| 场景 | 修复前平均 step / P95 | 修复后平均 step / P95 |
|---|---:|---:|
| 24 辆开阔地 | 0.114 / 0.301 ms | 0.175 / 0.500 ms |
| 48 辆开阔地 | 0.188 / 0.443 ms | 0.421 / 0.991 ms |
| 48 辆窄口 | 0.158 / 0.340 ms | 0.496 / 1.194 ms |
| 48 辆对向 | 0.132 / 0.287 ms | 0.333 / 0.825 ms |
| 48 辆绕障碍 | 0.165 / 0.345 ms | 1.074 / 2.626 ms |

碰撞与避让增加了 CPU 工作量；这次改善的是到达率和停稳，不能宣称 CPU 更快。测试中成本仍明显低于 50ms 模拟步长，但不包含 GPU 渲染，也不代表上千单位或长时间激战性能。

额外压力：200/400 辆混编通过同一个 288u 宽瓶颈，各模拟 60 秒。首轮暴露局部 A* 重评热点后，通过 FIFO 预算和分帧平滑降低开销：

| 数量 | 优化前平均 / P95 / 最差 | 最终平均 / P95 / 最差 | 60 秒通过瓶颈 / 到达终点 |
|---|---:|---:|---:|
| 200 | 8.39 / 23.02 / 58.97 ms | 4.55 / 8.73 / 26.87 ms | 199 / 73 |
| 400 | 19.06 / 45.42 / 98.20 ms | 10.62 / 18.11 / 41.77 ms | 298 / 77 |

两组压力的非数值坐标和越地形次数均为 0；每 0.5 秒检查的单位重叠为 0u，最大单步超出速度预算小于 5×10⁻¹³u（浮点误差）。不是所有单位能在 60 秒内通过拥挤瓶颈并走完长距离；400 单位也不能据此承诺 60FPS。压力计时仅包含模拟 step，另行运行的验证扫描不计入其中。

狭窄通道被静止单位完全堵住且没有退让空间时，后车应等待实际让开，不强行穿越。非常大的编队在岸边可能展开较宽；离散格网导航不能取代任意宽度通道的连续几何规划。
