## 结论

**有用，主要用于输入可靠性、拥堵调度、状态一致性和性能验证。** 它是《固体站连续生产控制台完整代码教程》，不是游戏引擎或武器建模教程。可以借鉴“单一状态所有者、命令受理不等于执行完成、完整物体包络、有限预算与公平排队、以实测结果验收”的工程方法。无需把 PLC、SQLite 事件库或机器人现场恢复系统搬进单机游戏。

当前游戏已经实现其中相当一部分方法。本次对照额外发现一个可立即修复的**开镜绘制统计重复计数**问题，并实测到**静止人员重复求解关节**的优化空间。前者会误导性能判断，后者需要基准验证后才能宣称帧率收益。均已发给主线程，本文不修改运行时。

主流程跟进：本轮已修复开镜统计，按实际 WebGL render 帧计数变化累计前景 pass；新增 7 项回归通过。以下复现描述保留修复前证据。静止 IK 缓存、拥堵诊断、预约通行和 LOD 仍为候选方案，未宣称已经落地。

## 可立即落地：先修计量，再优化冗余

### 1. 开镜统计重复计数——已 CPU 复现，建议本轮修

资料 §19 强调实际产量与推算值分开、诊断数据不能误导控制判断。这里可以直接落实到绘制计量：

- `src/battle3d.js:158` 先记录世界渲染的 `gl.info.render`；第 159 行只要 `firstPerson.view` 存在，就再次把同一计数作为前景加到总数。
- `src/direct-control.js:178–181` 的真实 `drawOverlay` 在 `opticalActive()` 为真时跳过前景 `view.render`。因此此时没有第二次渲染，计数仍是上一次世界渲染。
- CPU 探针调用实际 `WarDirectControl.prototype.drawOverlay`，执行从 `battle3d.js` 读取的统计分支，仅用假计数器替代 GPU。世界设为 137 次绘制/12,000 三角形；未开镜时前景实际执行一次并返回 3/100，得到 **140/12,100**；开镜时前景执行 **0 次**，却得到 **274/24,000**。

最小修复：由前景渲染路径明确报告是否真正渲染或返回本 pass 统计；未渲染时 `foregroundCalls/foregroundTriangles` 为 0，再合计。仅判断 `view` 存在不够，disposed/no renderer 的早退也应覆盖。

成本估计：0.5–1.5 小时含 CPU 与原生对照。收益：统计准确；**不会因此自动增加真实 FPS**。验收：不开镜、RMB、V、无 view、已销毁 view 五种状态；总数等于实际执行 pass 之和，开镜不可重复世界值。

本机库运行时 `THREE.REVISION` 实测为 `160`。[r160 官方 WebGLInfo 源码](https://raw.githubusercontent.com/mrdoob/three.js/r160/src/renderers/webgl/WebGLInfo.js) 中默认 `autoReset: true`，计数由实际绘制更新；[官方 WebGLRenderer 文档](https://threejs.org/docs/pages/WebGLRenderer.html) 说明默认每次 render 重置，多 pass 应明确累计。这里核对计数语义，不建议为此升级渲染器版本。

### 2. 静止单兵的重复 IK——已测出冗余，性能收益待测

`src/personnel-animation.js:56–64,82–102`：每个推进了模拟时间的静止人员仍求解左右腿、左右臂，普通持枪人员在末尾又把所有骨骼四元数归零。

CPU 探针创建 1 名中国 operator，初始化后保持位置/跳跃不变，推进 60×1/60 秒；临时计数 `THREE.Vector3.prototype.clone` 并恢复原函数，得到 **2,040 次 clone**，`moving=false, phase=0`。这仅计 Vector3.clone，不含直接 new 和 Quaternion，也不是 GPU 帧耗时测量。游戏真实模拟步为 0.05 秒，不能直接将本探针的 60 次更新冒称每秒实际工作量。

最小方案：稳定停姿已建立后跳过重复 IK；缓存中保留时间、位置及必要状态，以便重新移动/旋转、落地、隐藏后再现安全恢复。医疗兵有不同静止手臂姿态，须先建立其停姿再跳过；不能把“无位移”一律当完成归位。随后再考虑 solver scratch 向量复用。

成本估计：2–4 小时含 48 变体与生命周期回归。验收：姿态与现有结果一致，停止后无脚滑，暂停不动、重新移动正常、医疗兵双臂正确；稳定静止更新的 clone 数显著减少。固定同一场景分别测 50/200/500 人、静止/移动混合的 JS P50/P95/P99 与帧时间，再报告真实收益。模型精度不因这个优化降低。

### 3. 利用现有字段做轻量拥堵/帧预算诊断

资料 §11/19 的“等在哪里、等多久、瓶颈在哪”可利用现有 `crowdWaiting.id/since`（`crowd-navigation.js:66`）、`_crowdReplans`、`crowdRepathCount`；另记录 `app.js:1060–1066` 达到每帧 8 步上限并丢弃积压的次数。只在调试模式按低频汇总，不把同步文件写入放到逐实体循环。

成本估计：1–3 小时。收益：区分真实路不通、局部让行、重规划排队与 CPU 跟不上，帮助定位用户所说“走不到”；不是直接提高通过率。验收：同 seed、同命令脚本记录到达数量、到达时间、最大等待时间、重规划队列峰值、预算耗尽次数；开启诊断不改变最终位置、HP、资源和命令结果。

## 不适用：不照搬的部分

- **工业持久化执行账本、SQLite 每动作提交、PLC/Modbus/继电器驱动、现场 owner/fence：**文档为真实设备故障恢复服务。单机游戏当前 Game 已有统一所有者；每次开火持久化到数据库会增加依赖和 I/O。未来若做网络联机再单独设计服务器权威与命令序号。
- **工业暂停语义：**MD §16、PDF 第 39 页允许已提交设备动作继续排空；游戏 P 应保持当前冻结模拟规则。只有“释放右键停止新发射、在途弹仍结算”的区分可类比，不能让暂停后人物继续走或子弹继续扣血。
- **小车半宽、坐标阈值、称重/分料参数、机械臂点位：**是该固体站现场参数，不可作为坦克、船舰或单兵碰撞尺寸。应继续用游戏真实模型与可玩性测试生成导航包络。
- **武器外形、服装考据、DLSS/AI 光影、引擎升级：**资料没有提供相应图像、合法模型资产、实现或基准。它不能证明当前士兵还原实物，也不能证明有可直接复用的英伟达画质组件；继续使用已授权的公开参考和原生画面验收。
- **文档中的源码/测试清单：**可用于学习边界和测试分层，不是本项目已执行、已通过的证据。未经许可不整包复制其他项目代码；本次只迁移设计思路。
